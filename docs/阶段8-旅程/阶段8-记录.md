## 1. 什么是旅程，要解决什么

"用户在网页提交品牌后，程序依次经过哪些代码才出报告"：这种"一件事的路径"叫**旅程**。画布上的方块和线说的是"谁依赖谁"，旅程说的是"一件事怎么流"，两者不一样：流程常常穿过一个调度器，相邻两步之间未必直接依赖。

nativue 的旅程是 LLM 写的，画布照着高亮，没有任何校验。我们按设计稿 v1 第 6 节和 v1.1 第 11 步：

- 旅程是**假设**（T2）：入口 + 有序步骤，人或 AI 提。
- **静态检验**（T1）：相邻两步在 import / 调用图上有没有路，机器算，带证据行。
- **动态检验**（T3）：指定几个测试，带覆盖率跑一次，真实碰到全部步骤才算"已验证"；验证时记每步的代码哈希，之后代码变了就"验证过时"，重跑才算。
- "已验证"只有检验器能写。

用户 2026-10-22 拍板"动态检验留到第一版最后"，这一步就是第一版的最后一块。

## 2. 做法（技术、备选、为什么）

| 环节 | 用的技术 | 备选 | 为什么 |
|---|---|---|---|
| 入口候选 | 正则扫源码：FastAPI / Flask 的 `@x.get("/…")`、click / typer 的 `@x.command()`、`def main(`、`if __name__ == "__main__"`；JS 的 `app.get(`；带行号和紧随的函数名。T0 | 解析框架 | 只是给人挑起点的清单，正则够用；GEO 扫出 39 个 |
| 旅程怎么存 | `状态目录/journeys.yaml`（T2），每条 id、name、role、steps（file: 或 sym: 节点 + note）、verify.tests、author、时间；机器写的验证记录另放 `journeys-verified.json` | 和标注混在一个文件 | 人写的和机器写的分开，机器文件别手改 |
| 校验 | id 格式、名字职责长度、2 到 30 步、步骤必须存在且不能是目录、相邻不重复、验证用的测试文件必须在索引里、不含"已验证"；不通过整条退回 | 只查存在 | 和标注同一套"写入后标红"改成"写入时退回"的严格度，因为旅程错了会误导整条高亮 |
| 静态连通 | 文件级图 = import 边 + 调用边归到文件；相邻两步宽度优先找路，最多 4 跳。顺序：正向路（直接 / 经过 n 个文件）→ 同一个文件直接用到两步（"由 C 串起来"，调度器模式）→ 反向路（后一步用到前一步，数据回流或回调）→ 断链。两步都是函数时先在调用图上找 | 无向连通 | 无向图上几乎什么都连得上，没有信息量；分四种说法才看得出流程是怎么串的。每一跳带证据行，面板可点开 |
| 动态验证 | `glassbox journey verify <id>`：用项目自己的解释器 `coverage run -m pytest <指定测试>`，写到 `状态目录/test-results/journeys/<id>/`，不碰全量跑的结果；真实碰到的文件 = covered_lines > 0；记每步哈希 | 复用上次全量跑的覆盖率上下文 | 全量跑的覆盖率没记当时的代码哈希，不知道代码有没有变；它只做提示（"按上次全量跑，指定的测试碰到了 6 / 6 步"），真算 T3 要专门跑 |
| 状态 | 步骤不存在 → invalid；有验证记录：测试全过且碰到全部步骤 → verified（代码变了 → verified-stale），否则 failed；没记录：有断链 → broken，否则 hypothesis。动态和静态同时有时以动态为准，断链只作提示 | 静态断链就判死 | 静态图看不见动态分发，真跑过比推出来的可信 |
| 入口 | `glassbox journey list / set / verify / entries / skill`，服务开着走 HTTP；`GET/POST /api/journeys`、`POST /api/journeys/verify?id=` | 只做 MCP | 和标注一样，任何 AI 工具都能用 |
| 画布 | 空选面板列旅程，点一条：面板一步一步列出来，相邻步之间写连接方式和证据；画布上所有步骤的方块高亮，当前这一步再加一圈紫；上一步 / 下一步 / 看这一步会跳到那一步所在的目录（函数就进文件）；选了旅程还能点方块看细节，点空白回到旅程 | 只高亮不步进 | 规划稿 v0 的"操作旅程：按步骤高亮，上一步 / 下一步"原样做 |

## 3. 真相等级

| 显示的内容 | 来源 | 等级 |
|---|---|---|
| 旅程本身（名字、步骤、说明） | 人或 AI 写的 journeys.yaml | T2 声明 |
| 相邻步的连接（直接 / 经过 / 由谁串 / 反向 / 断链） | import 与调用图上找路 | T1 推导，证据行 T0 |
| 已验证 | 指定测试带覆盖率跑过，碰到全部步骤 | T3 验证 |
| 验证过时 | 验证时的步骤哈希 ≠ 现在 | T0 观测到的变化 |
| 入口候选 | 正则扫源码 | T0 观测 |

## 4. GEO 实测（服务开着，走 HTTP）

入口候选 39 个：`GET /`、`POST /jobs`、`GET /jobs/{job_id}/category`… 全在 report/routes.py；`main()` 和 `__main__` 在 diagnosis/access_audit.py 与 report/__main__.py。

交了 3 条旅程，1 条故意指向不存在的文件：

```
收下 2 条，退回 1 条
  ✗ 第 3 条 bad-journey：步骤不存在：file:report/nothing.py
```

**web-report 网页诊断全链路**（6 步：routes → jobs → scheduler → diagnose → narrative → summary，验证用 tests/unit/test_i18n.py 与 test_report_page.py）：

- 静态：routes → jobs 直接；jobs → scheduler 直接；scheduler → diagnose 没有正向路，由同时用到两者的文件串起来；diagnose → narrative 同理；narrative → summary 直接。提示"按上次全量跑的覆盖率，指定的测试碰到了 6 / 6 步"。
- 动态：`glassbox journey verify web-report` 跑了 46 个测试，通过 46、失败 0，真实碰到 74 个文件，79 秒。结论「已验证：2 个测试带覆盖率跑过，真实碰到了全部 6 步」（面板里状态词和说明分开显示），T3。这就是设计稿里"GEO 一条诊断旅程升级为 T3"的验收。

**site-audit 官网访问审计**（3 步，没指定测试）：静态通过，状态"假设"；crawler/fetch.py → diagnosis/findings.py 是反向（findings 隔 3 个文件用到 fetch），面板把这条链列了出来。

单元测试 57 个全过，新增 journeys.test.ts 4 个：入口候选四种、静态连通五种结果、校验六种退回、快照的假设 → 已验证 → 验证过时 → 验证没过。

## 6. 没做和要注意的

- 动态验证要 79 秒，因为两个测试文件各 20 多个用例还要起解释器；想快就指定单个用例 `tests/x.py::test_y`。
- "由 C 串起来"只看直接的共同调用者；更远的编排关系会落到"反向"或"断链"。
- 一条旅程只能指定 pytest；JS 项目没接。
