## 4. 规矩（用户定的，别破）

1. **画布是代码的函数**：结构只由机器推导；人和 AI 只写绑定到真实节点的标注；真相分级 T0 观测 / T1 推导 / T2 声明 / T3 验证，"已验证"只有检验器能写。
2. **所有界面文字是"人话（专业术语）"格式**，统一出处 `web/src/words.ts`；数字可点开看来源与等级。
3. **任务状态以代码为准**：任务文档只当计划清单，文档没更新是提示不是错误。
4. **不往 GEO 仓库写文件**。唯一例外是用户批的：2026-10-27 往 GEO 架构书末尾追加了「附录:v0.4.29 代码对照回写」，只追加不动正文；那个改动在 GEO 仓库里**没提交**，由管 GEO 的会话提交。
5. 读被观测项目的文本一律按 `\r?\n` 切行（E-039：GEO 文件被存成 CRLF 后任务栏空了）。
6. 每一步：先说做法（技术、备选、为什么），做完写记录 + 截图，更新错误库、记忆、README，`git commit`（`feat(阶段N): …`，末尾 `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`）并 push。
7. 用户不是程序员，解释要用简单中文；叫"宝宝"是习惯，不用在意。

## 6. 下一步候选（按我的推荐排）

1. **把 hooks 和两个 skill 装进 GEO 的 `.claude/`**：一条命令各一次，但要用户批。装了之后 GEO 那边的会话改文件会立刻进活动流、会话开始自动记基线、能自己写标注和旅程。
2. **JS/TS 项目的测试格式**：vitest / jest 的 junit 和 istanbul 覆盖率（`src/tests.ts` 现在只认 pytest 的 junit 和 coverage.py 的 json）；顺便在 glassbox 自己身上跑一遍画布（dogfooding）。
3. **字段级对照**（v1.2 §2.4 的余量）：架构书 6.2、6.3 的字段表对照 pydantic 模型的字段，索引器要收字段。
4. **标注质量**：docstring 抽的名字里以参数名开头的那批（像 run_plan 的"prior_runs"）人工改；`annotate show` 加个"疑似生硬"过滤。
5. **性能**：结果回来那一轮重算可以不重新索引（现在 1 秒）；去抖 1.5 秒可调短。
6. 旅程动态验证指定单个用例会快很多；MCP 入口没做（HTTP 已够）。
