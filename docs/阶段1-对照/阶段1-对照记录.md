## 2. 扫描器给出的事实（分析导入前）

- 178 个文件被索引，21 个目录模块，28 条 import 边。语言分布：Python 126、JSON 23、HTML 11、Markdown 10、YAML 5、Text 2、TOML 1。
- 目录即模块的结果：`.claude`、根目录、`docs/报告留档`、`docs/样子稿`、`tests/contract/golden/*` 四个金样目录各成一个模块，与"架构模块"无关，噪音明显。
- 画布：单列 "directory"，21 个模块纵向堆叠，全部标"推断"，描述为占位文字"按目录分组，职责待确认"。见 `01-分析前-目录图.jpg`。

### 2.1 跨层边核对（以项目自带的 tests/unit/test_layer_dependencies.py 为标准答案）

| 边 | 扫描器 | 守卫测试的裁决 |
|---|---|---|
| adapters → engine，6 处 | observed | 全部是 `engine.models`，白名单里唯一的"下层用上层"例外（契约类型） |
| engine → adapters，6 处 | observed | 允许，L2 → L1 |
| engine → crawler，6 处 | observed | 允许，L2 → L1 |
| diagnosis → crawler，1 处 | observed | 允许，且 access_audit 独立运行正是设计意图 |

## 3. 分析导入后

### 3.1 过程
- 一个子代理按 nativue 的分析协议只读通读 GEO 源码（185 个跟踪文件，约 20 分钟、26 万 token），产出 15 个模块、28 条目录间 import 边（118 条证据行）、3 条旅程（9 / 6 / 6 步）。
- 分析期间**另一个 Claude 会话提交了 GEO 仓库**（e26ca32 → 2eaa6c4，新增 engine/spellings.py 等 13 个文件）。nativue 的导入器按设计拒绝过期的 inputId，于是重扫、按文本锚点重新生成草稿、再导入。子代理为此把草稿做成了生成器而不是手抄行号，否则代码一动整份分析就作废。
- 转换脚本预校验后 `import-analysis` 一次通过。nativue 索引了 180 个文件，比 git 少 5 个：`.env.example` 被敏感文件规则排除，其余为它的大小或二进制规则跳过。

### 3.2 画布与面板
- 画布变成 9 个分组（按 kind）、15 个模块，全部"已观察"，每个有中文名与一句话职责。见 `02-分析后-语义图-全图.jpg`。
- 点模块：右栏显示职责、相关连线（方向、类型、置信度）、关联文件各带证据行与说明、跳转文件树。
- 旅程：三条可选，上一步 / 下一步 / 整条路径，步骤高亮画布模块，标"推断"。见 `03-旅程高亮.jpg`。
- 画布缺陷：固定布局，每个 kind 一列、模块纵向堆叠，9 列排成一条横带，缩到 15% 才能全览；边全挤在列间，看不出方向和层次。页面每秒整体重渲染，DOM 引用一秒内失效，对自动化测试也是麻烦。

### 3.3 它说对的
- 15 个模块的职责与架构书、CLAUDE.md 一致。
- 28 条边与守卫测试扫到的 import 集合一致。
- 旅程步骤与源码阅读一致，但未运行验证，所以只能标"推断"，这个标法是诚实的。

### 3.4 它说不出的
- adapters → engine 是白名单例外（守卫测试第 16 行，架构书附录 v0.4.3）。只能在证据 note 里写字，图上与普通边无区别。
- config 被五处按路径读取（surfaces.yaml、tiers.yaml、platforms.yaml、evidence_registry.yaml、crawlers.yaml），却是孤立节点；report/templates 同理。只画 import 边会漏掉资源依赖。
- report → crawler 实际是依赖注入：runner 把 Playwright / Reddit / Wayback 实现注入给 engine/page_check 的协议。图上与普通 import 无区别。
- engine ↔ engine/detectors 的双向边是同层内部结构，不是分层问题，但图上像一个环。
- 仓库在导入期间变了两次，画布无法显示"变了什么"。"本次更新"页签只显示任务，不显示代码差异。
- 测试是否通过、覆盖率多少，图上没有。

### 3.5 一个关键观察
这次导入的 28 条边**没有一条是 LLM 判断的**，全是生成器机械扫 import 得到的；真正由 LLM 写的只有模块名、职责和旅程。也就是说，结构层完全可以机器化，LLM 只需要写标签。这正是 glassbox 的原则。

## 4. 对 glassbox 的启示

1. **直接继承**：git ls-files 索引与隐私排除规则、证据结构（path + line + note）、导入校验、过期拒绝、保留上一张有效图。
2. **反转**：结构不能由 LLM 响应整体覆盖。机器图是唯一结构，LLM 只写绑定到节点的标签。本次实测证明了可行性。
3. **规则进图**的具体需求：白名单例外带出处；资源依赖边（按路径读取配置与模板）；依赖注入边的标注；同包子目录可折叠。
4. **基线差异最先补**：SessionStart 记 HEAD，git diff 投影到模块图。本次实测里仓库变了两次，图上一无所知。
5. **画布**：固定列布局在 9 组 15 模块时已难读。React Flow + ELK、按层分泳道的决定得到验证。
6. **实时实现**：数据不变时不应整页重渲染。SSE 增量更新 + 稳定节点 key。
7. **成本**：全量语义分析一次 26 万 token，不可持续。标注必须按节点内容哈希增量，只重写变了的。
