# 架构落地率记录：架构书写的，代码里有没有

日期：2026-10-27。设计稿 v1.2 第 2.4 节定的表盘，对应提交见 git log「feat(架构落地率)」。

## 1. 要解决什么

架构书是蓝图，代码是现实。两者对不上有两种：蓝图没落地（书里写的模块、接口代码里没有），和文档落后（代码里有的书里没提）。以前只能人肉逐条对照；v1.2 要求机械算：声明（T2）对照索引（T0），每项标存在 / 缺失，落地率 = 存在数 / 声明数，缺失与多出各列一表。

## 2. 做法（技术、备选、为什么）

| 环节 | 用的技术 | 备选 | 为什么 |
|---|---|---|---|
| 架构书在哪 | overlay `architecture.file`；没指定就找根目录名字带「架构」或 architecture 的 .md；原文由索引器一起读（它本来就缓存所有文本文件） | 单独读文件 | 和任务列表同一条路，书改了画布也跟着变 |
| 从书里抽什么 | 四种来源，全是正则：① 目录树代码块（`├── engine/`、`│   ├── models.py`，按缩进拼出完整路径）；② 接口伪代码块（`interface SurfaceAdapter:`、`ask(request) -> SurfaceRun`、一行一个的数据模型名）；③ 反引号里的路径、带括号的函数名、驼峰类名；④ 正文里的驼峰词 | 让 LLM 读书列清单 | 机械抽的每一项都带书里的行号，可点开；LLM 列的清单本身又是声明，没法当对照的基准 |
| 强弱声明 | ①②③是强声明，算进落地率；④正文驼峰词是弱声明，只做提示 | 全算 | 正文里的驼峰词一半是产品名、外部名字（FatCat、HubSpot、LinkedIn、DasGupta），算进去落地率失真；同一个词只要在代码块或反引号里出现过就升为强声明 |
| 哪些不算 | 依赖清单里的库名（技术栈面板已经算出来的）、常见技术名、Python 内置异常；全大写的常量不抽 | 手写名单 | 清单来自项目自己的 pyproject，不用人维护 |
| 怎么对照 | 文件：路径完全相等；只写了文件名没写目录的，恰好一个同名文件就认它；目录：底下有文件。类：同名的类，退而求其次同名的任何符号（标"写法不同"）；函数：同名的函数或方法。缺失的给提示：同名文件在哪、相近的名字（AdapterTransientError ↔ TransientError） | 模糊匹配算存在 | 相近只提示不算存在，否则改名没改书这种事就被盖住了 |
| 多出 | 代码里的顶层目录、源文件、类，书里一个字没提的 | 无 | v1.2 原文：提示文档落后 |
| 按章节 | 每条声明归到最近的标题，面板和命令行列"缺了东西的章节"，全部落地的只给个数 | 平铺 | GEO 的书 50 多个标题，平铺看不过来 |

## 3. 真相等级

| 显示的内容 | 来源 | 等级 |
|---|---|---|
| 书里声明了什么 | 架构书原文，正则抽的，带行号 | T2 声明 |
| 存在 / 缺失 | 索引里的文件与符号 | T0 观测 |
| 落地率 | 存在数 / 强声明数 | T1 推导 |
| 相近的名字、同名文件在哪 | 索引 | T1 推导，只提示 |

## 4. GEO 实测（`glassbox arch <GEO> --overlay … --no-precise`）

```
架构落地率 87.4%：GEO工具项目架构书v0.4.md 声明了 174 项（文件和目录 107、类和函数 67），代码里存在 152，缺 22
  2.3 代码仓库目录结构(建议)：27 / 29，缺 adapters/perplexity_search.py、tests/fixtures
  12. 契约改动清单：3 / 5，缺 InformationNeed、PromptVariant
  S2 实施记录：6 / 11，缺 NeedDiagnosis、NeedIntent、ProportionEstimate、mc_coverage.py、calibrate_generations.py
  …
  另 30 个章节全部落地
```

缺的 22 项每条都对得上一个真实原因：

- `adapters/perplexity_search.py`：任务列表 S1 写着"删 Perplexity 搜索接口"，代码删了，第 2.3 节的目录树没改。
- `tests/fixtures`：目录树里规划了"HTTP 录制样本"，从没建过。
- `TransientError`：代码里叫 `AdapterTransientError`，工具提示"有相近的名字"。
- `InformationNeed`、`PromptVariant`：第 6 章的核心契约名，S2 测量方法换代后代码里换了叫法，书的正文没回写。
- `config/judge.yaml`：代码里是 `judges.yaml`。

弱声明 30 个：13 个代码里有，17 个没有（FatCat、HubSpot、LinkedIn、DasGupta、SearchBot…），不算进落地率。多出：书里没提的源文件 17 个、类 90 个（各家适配器类、RedditFetcher、RenderedPage…），说明书比代码落后了几个版本。

第一版规则（正文驼峰词也算、只写文件名的不认）得到 73.3%，缺 55；按上面两条修正后 87.4%，缺 22，剩下的都是真的。

单元测试 60 个全过，新增 architecture.test.ts 3 个：四种来源的抽取与强弱、对照与落地率与按章节与多出、自动找架构书。

## 5. 画布

空选面板「架构落地率」段：百分比、声明数、缺了东西的章节、展开缺失清单（每条可点开书里那一行，带提示）、正文驼峰词一句话、展开"代码里有书里没提的"；顶栏「架构落地 87.4%（书里写了 174 项，缺 22）」。

## 6. 没做

- 字段级对照（6.2 AskRequest 的字段表、6.3 SurfaceRun 的树）：索引不收类的字段。
- 依赖方向的声明（"L4 → L3 → L2 → L1"）已由守卫测试机械把守，这里不重复。
- 书里一句"改为"、"下线"之类的历史叙述照样会抽出旧名字；按章节看就能分辨"修订记录"和"正文"。
