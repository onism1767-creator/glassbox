# 自动跑相关测试：改了文件只跑和它相关的测试，结果几秒内进画布

日期：2026-10-27。接着[测试接入记录](记录.md)做的，对应提交见 git log「feat(测试): 自动跑相关测试」。

## 1. 要解决什么

上一步测试结果能进画布，但要手动跑一次 `glassbox test`，GEO 全套带覆盖率 284 秒。开发时真正想要的是：Claude 改了一个文件，几秒后画布上这个文件、它所在的目录、提到它的任务就变红或变绿，不用等整套跑完，也不用自己记得去跑。

## 2. 做法（技术、备选、为什么）

| 环节 | 用的技术 | 备选 | 为什么 |
|---|---|---|---|
| 什么时候触发 | 复用阶段 5 的文件监听和 hook：一轮增量重算完，拿到"这次哪些 .py 变了"，交给调度器；最后一次改动后再等 1.5 秒（合并连续改动）才跑；Claude Code 的 Stop hook 到了就不等了马上跑 | 只靠 PostToolUse hook 触发 | 监听覆盖所有改动来源（Claude、人、git checkout），hook 没装也能用；装了 hook 多一个"本轮结束立刻跑"的信号 |
| 跑哪些 | 四条规则按文件判：① 它本身是测试文件 → 跑这个文件；② conftest.py → 跑它所在的整个目录；③ 上次结果里知道"哪些测试跑过它"（覆盖率上下文，T0）→ 跑这些用例；④ 没有上下文但有测试文件 import 它（T1）→ 跑那些测试文件的用例。都不是 → 不跑，活动流里说明 | 按文件名猜（`x.py` ↔ `test_x.py`）；永远跑全套 | 覆盖率上下文是机器看到的事实，精确到用例：改 `app/service.py` 只跑到过它的那 1 个用例，不跑同文件里没碰它的另一个 |
| 用例怎么传给 pytest | 用 junit 的用例 id 反推 pytest 的 node id（`tests/unit/test_a.py::TestX::test_y`），参数化的 `[..]` 去掉，pytest 会把所有参数都跑；命令行超过 12000 字就退到按测试文件传；node id 失效（测试改名）pytest 退出码 4 → 自动按文件重跑一次 | 写临时的 pytest 参数文件 | Windows 命令行上限 32767 字；按文件退化简单可靠 |
| 跑的时候 | `python -m pytest -p no:cacheprovider -q --junitxml=状态目录/test-results/partial/junit.xml <目标>`，不带覆盖率 | 带 `coverage run --append` | 部分运行的覆盖率会把全量的数字冲掉（只跑 1 个用例时文件覆盖率会掉到几成）；覆盖率只在全量跑时更新，画布上写明"覆盖率来自上次全量跑" |
| 结果怎么合并 | 范围内的用例（这次传给 pytest 的 id、文件、目录能覆盖到的）换成新结果，范围外的保留上次的；删掉的测试文件的旧用例一并拿掉；写成 `状态目录/test-results/results.json`（带 `partial` 元信息和 `fullAt`）。读的时候 results.json 比 junit.xml 新就用它，`glassbox test` 全量跑一次又会把它盖过去 | 直接改写 junit.xml | junit.xml 是 pytest 写的事实，不动它；results.json 是我们自己的合并视图，格式自己定 |
| 画布怎么知道 | 结果写好 → 调度器直接要求重算（不依赖文件监听）→ 快照 → SSE `update`；跑的时候另发 SSE `autotest`，顶栏显示"正在跑约 N 个相关测试（改了 x.py）…" | 只靠结果目录的监听 | 监听有时漏、有时重复；直接通知确定性高，监听留作备份 |
| 开关 | 缺省开，前提是找得到带 pytest 的解释器（仓库 `.venv`，或 overlay `test_results.python`）；`glassbox serve --no-auto-test` 或 overlay `test_results.auto: false` 关；`test_results.debounce_ms` 调等待 | 缺省关 | 没有解释器就自动关并在面板上说明原因，不会误跑 |

## 3. 真相等级

| 显示的内容 | 来源 | 等级 |
|---|---|---|
| "这些测试跑过它" | 上次全量跑的覆盖率上下文 | T0 观测 |
| "测试文件 import 了它" | import 图 | T1 推导 |
| 通过 / 失败 | 这次 pytest 的 junit | T0 观测 |
| 其余用例的结果 | 上次全量跑的 junit | T0 观测，但标明时间（"来自 42 秒前的全量跑"） |
| 覆盖率 | 上次全量跑 | T0 观测，部分跑不更新 |

## 4. 实测（夹具 mini-live，3 个测试，解释器借用 GEO 的 .venv）

改 `app/service.py`（加一行注释）到画布上出现合并后的结果：

| 时刻（相对写文件） | 发生了什么 |
|---|---|
| +1.3 秒 | 增量重算完成，SSE update（1.1 秒重算） |
| +2.9 秒 | 1.5 秒去抖到期，开始跑：活动流「自动跑相关测试：约 1 个用例（app/service.py：覆盖率上下文说这些测试跑过它）…」，顶栏紫字"正在跑" |
| +4.2 秒 | pytest 跑完（1.4 秒，主要是解释器启动），results.json 写好 |
| +5.3 秒 | 重算完成，画布更新：「自动跑了 1 个相关测试：通过 1、失败 0、跳过 0，1.4 秒 → 总计 3 通过」 |

只跑了 1 个用例：`test_service.py` 里两个测试，覆盖率上下文说只有 `test_run_returns_model` 跑过 `service.py`，另一个没碰它所以没跑。

把 `run()` 改成返回错的类：同样流程后顶栏变红「测试 2 通过、1 失败」，`service.py` 方块标出失败的测试，面板里 ✗ 那一条带断言信息；改回去再变绿。见截图 03、04。

单元测试 38 个全过，新增 autotest.test.ts 4 个：四条选择规则与跳过、命令行过长退化与删除的测试文件、合并替换范围内保留范围外并记 fullAt、删掉的测试文件的旧用例移除。

## 5. 没做和要注意的

- 5.3 秒里 2.2 秒是两次重算（改文件一次、结果回来一次），1.5 秒是去抖。结果回来那次可以不重新索引只重读结果，去抖也可以调短；先不动，等 GEO 上用一阵看体感。
- GEO 仓库由另一个会话在改，这次没在 GEO 上实测自动跑；服务已换成新代码，它下次改 .py 文件就会跑。GEO 单个用例也要先起 pytest 和导入整个项目，预计 3 到 10 秒。
- 部分跑不更新覆盖率；想刷新覆盖率还是 `glassbox test`。
- 只认 Python 和 pytest；JS 项目的 vitest/jest 没接。
- 跑测试会和被观测项目自己跑的测试并发，读同一份代码，写只写到状态目录，不会互相覆盖文件；但 CPU 会抢。
